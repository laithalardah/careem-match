## Steps (do in order, stop after each for a quick report)
1. **Rooms API skeleton** (`main.py`, `rooms.py`): all v2 endpoints, in-memory dict, 6-char room codes, `version` bump on every change, host-only checks (403), stage guards (409), CORS `*`, bind 0.0.0.0, `PUBLIC_APP_URL` env for `join_url` (`{PUBLIC_APP_URL}/#/join/{code}`). A level advances for everyone only when all participants are done. Level 1 cards = categories, level 2 = restaurants. Use fallback.json data for now. pytest + FastAPI TestClient for the state machine (join, host-only, advance, 409s).
2. **Catalog and cards** (`catalog.py`): build candidates from the MCP (`food_merchant_search` queries per category, `food_get_restaurant_menu` for availability, rating, ETA, dishes, prices). Cache in memory. Map meal -> cuisines (breakfast: Breakfast, Healthy; lunch: Arabic, Shawarma, Healthy, Italian; dinner: all savoury; dessert: Dessert/Bakery, empty state if none). Restaurant card description is generated from cuisine + top dishes (one sentence, no invented facts). `FALLBACK=1` serves everything from fallback.json with no MCP calls.
3. **History** (`history.py`): `HistoryProvider` interface returning per-participant {cuisine: weight, restaurant: weight} from `get_activities` (food, past, paginate with next_cursor), recency-weighted `0.5^(age_days/30)`, normalised 0..1. Modes via `HISTORY_MODE`: `host_only` (real history for the host, neutral for others), `demo` (clearly labelled seeded histories per participant, deterministic by join order, flagged `source:"demo"` in the trace). The MCP is single-user, so say this in a code comment.
4. **Scoring** (`scoring.py`): implement the algorithm exactly as in docs/v2-plan.md section 3: `u_p(r) = 0.5*s_p(r) + 0.2*s_p(cat) + 0.2*h_p + 0.1*q`, `U(r) = mean - 0.5*std`, veto (relax with a "compromise" flag if it empties the list), top-3 shortlist, keep per-person scores for `scores` in the result. Pure functions with unit tests (veto, fairness penalty, history tie-break, empty list).
5. **Deterministic planner** (`planner.py`): picks top-1, calls `food_get_restaurant_menu` and `food_get_items_options` (read-only, retry lookups up to 2 times, NEVER retry mutating tools), resolves required options to the cheapest default, assigns dishes per person (prefer liked/ordered dishes, 1-2 each), prices from menu + option prices, writes `agent_trace`. Re-plans to the next shortlisted restaurant on: closed, upstream error, dish unavailable, options required and unresolvable. No overlap -> `no_match`. This is the fallback and must always work.
6. **Bedrock agent** (`agent.py`): Converse API, model `global.anthropic.claude-sonnet-5-5`, us-east-1, tool use, loop capped at 8 iterations, fresh client per call via `bedrock_client.make_client()`. Tools exposed to the model: read-only MCP tools only (`food_get_restaurant_menu`, `food_get_items_options`, `food_search_restaurant_items`, `cart_get_basket_price` only if it is read-only and safe) plus a final `submit_plan` tool with a strict JSON schema {restaurant_id, lines:[{participant_id, item_id, option_ids}], reasoning, per_person:[{participant_id, why}]}. System prompt includes the safety rules below. The model gets the shortlist + evidence (votes, history, per-person scores) and must choose from the shortlist only. After `submit_plan`, a code validator rejects invalid plans (restaurant not in shortlist, unknown or inactive item, missing person, price recomputed from menu). On any Bedrock error, validator rejection after one repair attempt, or iteration cap, fall back to the planner (step 5) and add a trace line saying so. Record every tool call in `agent_trace` (iteration, tool, input, short output_summary, failed flag). Show the token/time cost in the log, not in the API.
7. **Group order** (`order.py`): `POST /rooms/{code}/order` (host only = the explicit approval). Mode food: call `cart_add_items` ONCE for the whole group at the matched restaurant (each line has `comment: "for NAME"`, options as `catalog_option_id` + count, domain "food"), then read `cart_get_basket_price` and return `{status:"basket_ready", price_breakdown, restaurant_link, message}`. Never retry cart_add_items automatically; on timeout/failure return `failed` with a readable message and let the host retry. NEVER call `cart_checkout`, `cart_grocery_checkout` or any order-placing tool, unless I explicitly say so in chat. Mode dineout: no cart call, return `{status:"go", restaurant_link}`.
8. **Resilience and demo**: `FALLBACK=1` whole-flow mode; startup check that prints which MCP and `.env` are in use (never print secrets); a `scripts/demo_room.py` that creates a room, joins 3 fake people, swipes, runs the match and prints the result; document how to run (`uvicorn main:app --host 0.0.0.0 --port 8000`).

## Safety rules (also put them in the agent's system prompt)
- Never auto-confirm a mutating tool: the host's tap on "Create group order" is the only approval. Never blindly retry a mutating tool. Retrying lookups is fine.
- In the sandbox cart tools are OK for testing; never call checkout or any order-placing tool unless I say so.
- Tool errors are readable messages: explain them and decide whether a retry makes sense.
- Location Amman, Jordan. The sandbox data is Dubai/AED: use the currency returned by the MCP and do not convert.
- AWS credentials are temporary (expire hourly): never cache them, never log or print them, never commit `.env`. If Bedrock says the token expired, return the fallback result and log "credentials expired, run refresh_env.ps1".
- No secrets in the app or in any response.
