## Decisions already made
- Order history: the host's history is REAL (`get_activities`, food, past). Every other participant is a **demo friend (bot)**: seeded taste persona + seeded history, flagged `is_bot` and `source:"demo"` in the trace. Real people can still join as guests; they just have no history (swipes dominate).
- Disputes are resolved by a group vote between **spin the wheel** and **split into groups** (details below).
- Group order = one basket per restaurant under the host's account; never check out.

## Steps (in order, stop after each for a quick report)
1. **Rooms API skeleton** (`main.py`, `rooms.py`): all v2.1 endpoints, in-memory dict, 6-char room codes, `version` bump on every change, host-only checks (403), stage guards (409), CORS `*`, bind 0.0.0.0, `PUBLIC_APP_URL` for `join_url` (`{PUBLIC_APP_URL}/#/join/{code}`). A level advances for everyone only when all participants are done. Level 1 = categories, level 2 = restaurants. Use fallback.json data for now. pytest + TestClient for the state machine.
2. **Catalog and cards** (`catalog.py`): candidates from the MCP (`food_merchant_search` per category, `food_get_restaurant_menu` for availability, rating, ETA, dishes, prices), cached in memory. Map meal -> cuisines (breakfast: Breakfast, Healthy; lunch: Arabic, Shawarma, Healthy, Italian; dinner: all savoury; dessert: empty state if none). Restaurant card description = one sentence from cuisine + top dishes, no invented facts. `FALLBACK=1` serves everything from fallback.json with no MCP calls.
3. **History + demo friends** (`history.py`, `demo.py`): `HistoryProvider` returning per-participant {cuisine: weight, restaurant: weight}, recency weight `0.5^(age_days/30)` normalised 0..1. Host = real `get_activities` (paginate `next_cursor`). Bots = seeded personas (Jordanian first names, e.g. Lina, Omar, Sara, Khaled; each with loved/disliked cuisines and 1-3 seeded past orders from the sandbox restaurants). `POST /rooms/{code}/demo-friends` (host only, needs `DEMO=1`, `/health` returns `demo`): count 1-4, scenario `consensus` (matching tastes), `dispute` (tastes that split the group into 2 blocs), `random`. Bots run in a background task: swipe each card with a 1.5-4 s delay following their persona (like loved, skip disliked, small noise), vote on the dispute method, and move/accept groups on their own. A code comment must say the MCP is single-user so history is real only for the host.
4. **Scoring** (`scoring.py`): exactly as docs/v2-plan.md section 3: `u_p(r) = 0.5*s_p(r) + 0.2*s_p(cat) + 0.2*h_p + 0.1*q`, `U(r) = mean - 0.5*std`, veto (relax with a "compromise" flag if it empties the list), top-3 shortlist, per-person scores kept for `scores`. Pure functions with unit tests (veto, fairness penalty, history tie-break, empty list).
5. **Dispute engine** (`dispute.py`):
   - Consensus = a restaurant liked by >= `CONSENSUS_THRESHOLD` (default 0.6) of participants with no veto. Checked when everyone finishes level 2, or when the host calls `/dispute/start` after `DISPUTE_MIN_SWIPES` (default 5) swipes each. Nobody liked anything -> `no_match` (not a dispute).
   - Otherwise stage `dispute`. Contenders = restaurants with at least one supporter (max 3). Supporters = people whose own top choice (highest `u_p`) it is; neutral people go to the contender with their highest utility.
   - `POST /dispute/vote`: majority picks `method`, ties go to the host's vote; when every person (bots too) has voted, or the host breaks the tie, set `method`.
   - **Wheel**: `POST /dispute/spin` (host, method == wheel). Slices weighted by supporter count (`weight`). Draw the winner SERVER-side with the `secrets` module, compute `final_angle_deg` so the pointer lands in the winner's slice, set `spin_id`, `spin_started_at_ms`, `duration_ms` (default 5000). After `duration_ms + 2000` ms the server forces that restaurant into the agent and moves to `matching`. Spinning twice is a 409.
   - **Split**: `split.groups` = one group per contender, members pre-assigned as above. `POST /dispute/move` lets anyone move themselves until the host confirms (empty groups vanish; if everyone ends up in one group treat it as `consensus`). `POST /dispute/confirm` (host) -> `matching`, one plan per group.
   - Tests: 2 vs 2 split, 3 vs 1, three-way split, tie-break by host, wheel weights over many draws are close to the weights, double-spin 409, everyone moves into one group.
6. **Deterministic planner** (`planner.py`): for each group (or the single winner) call `food_get_restaurant_menu` and `food_get_items_options` (read-only; retry lookups up to 2 times; NEVER retry mutating tools), resolve required options to the cheapest default, give each person 1-2 dishes (prefer liked/ordered), price from menu + option prices, write `agent_trace`. Re-plan to the next shortlisted restaurant on: closed, upstream error, dish unavailable, options unresolvable. This is the fallback and must always work.
7. **Bedrock agent** (`agent.py`): Converse API, model `global.anthropic.claude-sonnet-5-5`, us-east-1, tool use, loop capped at 8 iterations per group, fresh client per call via `bedrock_client.make_client()`. Tools: read-only MCP tools only (`food_get_restaurant_menu`, `food_get_items_options`, `food_search_restaurant_items`, price lookups that are read-only) plus a final `submit_plan` tool with a strict schema {restaurant_id, lines:[{participant_id, item_id, option_ids}], reasoning, per_person:[{participant_id, why}]}. The model gets the shortlist (or the forced restaurant) plus evidence (votes, history incl. `source:"demo"`, scores) and must choose from the shortlist only. A code validator rejects invalid plans (restaurant not allowed, unknown or inactive item, missing person, price recomputed from menu). On a Bedrock error, a rejection after one repair attempt, or the cap, fall back to the planner and add a trace line saying so. Log time and token cost, not in the API.
8. **Result shape**: always return `groups` (length 1 unless split), `resolution.type` (`consensus` | `wheel` | `split`), top-level fields mirroring `groups[0]` when there is one group, `restaurant: null` when split, `scores` and `agent_trace`.
9. **Group order** (`order.py`): `POST /rooms/{code}/order` (host only = the explicit approval). Food mode: for each group call `cart_add_items` ONCE for that merchant (each line `comment: "for NAME"`, options as `catalog_option_id` + count, domain "food"), then read the price with the read-only price tool, return per-group `{status, price_breakdown, restaurant_link, message}`. Never retry cart_add_items automatically; on failure return `failed` with a readable message so the host can retry. NEVER call `cart_checkout`, `cart_grocery_checkout` or any order-placing tool unless I say so in chat. Dine out: no cart call, return `{status:"go", restaurant_link}` per group.
10. **Resilience and demo**: `FALLBACK=1` whole-flow mode; startup check printing which MCP and `.env` are used (never secrets); `scripts/demo_room.py` that creates a room, adds demo friends, runs a consensus case and a dispute case (wheel and split) and prints results; document how to run (`uvicorn main:app --host 0.0.0.0 --port 8000`, `DEMO=1`).

## Safety rules (also put them in the agent's system prompt)
- Never auto-confirm a mutating tool: the host's tap on "Create group order" is the only approval. Never blindly retry a mutating tool. Retrying lookups is fine.
- In the sandbox cart tools are OK for testing; never call checkout or any order-placing tool unless I say so.
- Tool errors are readable messages: explain them and decide whether a retry makes sense.
- Location Amman, Jordan. Sandbox data is Dubai/AED: use the currency the MCP returns, do not convert.
- AWS credentials are temporary (expire hourly): never cache, log or commit them. If Bedrock says the token expired, return the fallback result and log "credentials expired, run refresh_env.ps1".
- Random choices (the wheel) come from `secrets`, server-side only, never from the client.
